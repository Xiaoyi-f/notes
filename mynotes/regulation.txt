Tip: 内网链路更短、转发节点少、带宽独享、无公网限速 / 干扰，所以速度远快于外网 

REST[Representational State Transfer（表现层状态转移）] 规范 --> RESTful是一个形容词: 表示遵守REST规范的
>= HTTP/1
传输: TCP
写好接口文档，方便接口连接:
    URL
    Method
    Data
将 REST 规范 类比为 "写信":
信封地址: URL
信封抬头 写上你要做的动作/行为:
    GET：表示“我要获取信息”
    POST：表示“我要提交数据”
    PUT：表示“我要替换全部数据”
    DELETE：表示“我要删除数据”
信封内容: 主要以 Json 形式

gRPC[gRPC Remote Procedure Calls（gRPC 远程过程调用）] 规范
== HTTP/2 --> 多路复用: 一次网络传输可以携带多个请求/响应
传输: TCP
跨类型、跨语言、速度快
基本规范:
1. 服务定义规范（用 .proto 文件）
你必须用 Protocol Buffers（Protobuf） 的语言来定义：
有哪些 Service（服务）
每个 Service 里有哪些 RPC 方法（函数）
每个方法的请求参数和返回值的数据结构

示例（.proto 文件片段）：
protobuf
service WeatherService {
  rpc GetWeather (CityRequest) returns (WeatherResponse);
}

message CityRequest {
  string city = 1;
}

message WeatherResponse {
  int32 temperature = 1;
  string condition = 2;
}
👉 这就是合同：任何语言实现的客户端和服务端，都必须遵守这个定义
2. 消息格式规范
数据在网络上传输时，必须编码成 Protobuf 二进制格式
它比 JSON/XML 更小、更快，但人类不可读
规范还约定了字段编号、类型映射（如 string、int32、repeated 等）
3. 传输协议规范
gRPC 规定必须使用 HTTP/2 作为底层传输协议
HTTP/2 带来的约定：
多路复用（一个连接并发处理多个请求）
头部压缩
支持服务器主动推送
4. 四种通信模式规范
模式	约定内容
一元调用	客户端发一个请求，服务端回一个响应（最像普通函数调用）
服务端流	客户端发一个请求，服务端可连续返回多个响应（类似下载流）
客户端流	客户端可连续发多个请求，服务端最后回一个响应（类似上传）
双向流	双方同时互相发送消息（类似 WebSocket，但有严格的消息边界）
5. 错误处理规范
使用标准的 gRPC 状态码（如 OK、NOT_FOUND、INVALID_ARGUMENT、DEADLINE_EXCEEDED 等）
不同于 HTTP 状态码（200、404），gRPC 有自己的一套数字+语义
6. 超时与取消规范
客户端可以设置 deadline（截止时间），超时后服务端会主动停止处理
支持取消正在进行的 RPC 调用（链式传播取消信号）
7. 安全规范
默认推荐使用 TLS/SSL 加密连接
也支持不加密的纯文本（insecure），但生产环境强制要求加密

websocket 规范 (无单一规范):
>= HTTP/2
持续连接，快速响应，占用资源(资源管控)
协议分类: wss(安全型) ws

JWT(JSON Web Token)
传统方式（Session）：
你买票入园，工作人员在电脑里记下"张三今天入园了"
每次玩项目，工作人员都要去电脑查"张三有没有票？"
问题：如果电脑（服务器）坏了或人多查询慢，就尴尬了

JWT 方式：
你买票后，工作人员给你一张加密的卡牌（卡牌上写着"张三，VIP，有效期今天"）
每次玩项目，刷一下卡牌就行，工作人员不用查电脑
卡牌本身就能证明你是谁、有什么权限

通俗理解: 一张自带信息的、防伪的、可以在各个服务间通用的电子凭证


业务逻辑推理方法:
1. 简单/小项目 直接依据UI一步一步关联思考需要的字段和关系以即处理 
2. "事令实状"四步法:
  第一步：事件风暴，抓核心事件
  · 目标：与业务专家一起，用便利贴写出系统中发生的关键业务事件（过去时态）
  · 示例：“订单已提交”、“库存已扣减”、“支付已完成”、“退款已发起”
  · 产出：事件时间线，理清业务核心流程

  第二步：寻找决策命令与角色
  · 目标：对每个事件，问“谁（角色）通过什么命令触发了这个事件？”
  · 示例：用户执行“提交订单” → 触发“订单已提交”
  · 产出：命令、角色、以及命令执行所需的输入数据（初步字段）

  第三步：抽取实体与聚合
  · 目标：将事件和命令中反复出现的名词（用户、订单、商品、库存）抽象为实体。找出聚合根（如订单聚合根包含订单行、收货地址）
  · 关键：明确不可变规则（例如：已支付的订单不能修改收货地址）
  · 产出：实体关系图、聚合边界、每个实体的核心属性（字段）

  第四步：定义状态机与约束
  · 目标：为每个核心实体（如订单、审批单）画出状态迁移图。列出所有业务不变量（例如：退款金额不能大于实付金额）
  · 产出：状态图、业务规则表（可作为数据库约束或代码校验）
