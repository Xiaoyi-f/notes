# 01 - 二进制帧结构设计——你和嵌入式开发者的"语法规则"

---

## 一、为什么需要自定义数据协议？

### 场景：设备要上报温度和湿度

```
方案1：直接发字符串
设备发送："Temperature: 25.5, Humidity: 60"
  ❌ 问题：太长、解析麻烦、占用带宽

方案2：发JSON
设备发送：{"temp":25.5,"humi":60}
  ✅ 优点：可读性好，你解析方便
  ❌ 缺点：嵌入式端生成JSON消耗资源（要字符串拼接）

方案3：发二进制帧（最紧凑）
设备发送：AA 55 01 00 0A 00 FF 00 3C 3B
  ✅ 优点：最短、解析最快、最省内存
  ❌ 缺点：可读性差，需要文档说明每个字节含义
```

**实际项目中**：
- 资源受限设备（STM32/ESP32做简单任务）→ **二进制协议**
- 能力强的设备（树莓派/Linux网关）→ **JSON/Protobuf**
- 调试阶段 → **字符串/JSON**，方便查看
- 量产阶段 → **二进制**，节省带宽和功耗

## 二、二进制帧的基本结构

```
一个典型的数据帧：

┌─────┬─────┬──────┬──────┬────────┬────────┐
│帧头  │长度  │命令字 │设备ID │  数据   │ 校验   │
│2字节 │1字节 │1字节  │1字节  │ N字节   │1字节   │
├─────┼─────┼──────┼──────┼────────┼────────┤
│AA 55│ 0C  │ 01   │ 01   │ ...    │ 3B    │
└─────┴─────┴──────┴──────┴────────┴────────┘
│     │     │      │      │        │
│     │     │      │      │        └── 校验和（确保数据没损坏）
│     │     │      │      └────────── 实际数据（温度、湿度等）
│     │     │      └───────────────── 哪个设备发的
│     │     └──────────────────────── 这是什么类型的数据
│     └────────────────────────────── 整个帧有多长
└──────────────────────────────────── 标识一帧数据的开始

总长度 = 帧头(2) + 长度(1) + 命令(1) + 设备ID(1) + 数据(N) + 校验(1) = 6+N 字节
上面的例子：0C = 12 = 6 + 6，所以数据区有6字节
```

### 每个字段的作用

| 字段 | 长度 | 作用 | 例子 |
|------|------|------|------|
| **帧头** | 2字节 | 标识数据包开始，方便从乱序的数据流中找到完整帧 | `AA 55`（很少出现在正常数据中） |
| **长度** | 1-2字节 | 告诉接收方这帧有多少字节，方便分配缓冲区 | `0C` = 12字节 |
| **命令字** | 1字节 | 标识这是什么类型的数据/指令 | `01`=读温度，`02`=读湿度，`03`=控制LED |
| **设备ID** | 1-2字节 | 标识是哪个设备发的 | `01`=1号设备 |
| **数据** | N字节 | 实际内容 | 温度值、湿度值等 |
| **校验** | 1-2字节 | 验证数据传输过程中是否出错 | XOR校验或CRC8 |

## 三、一个完整的例子：温湿度上报帧

### 协议定义文档（你和嵌入式开发者一起写的）

```
═══════════════════════════════════════════════════════════════
                温湿度传感器通信协议 V1.0
═══════════════════════════════════════════════════════════════

【帧格式】
┌──────┬──────┬──────┬──────┬──────────┬──────┐
│ 帧头  │ 长度  │ 命令  │ 设备ID│   数据    │ 校验  │
│2字节  │1字节  │1字节  │1字节  │  N字节    │1字节  │
└──────┴──────┴──────┴──────┴──────────┴──────┘

【字段说明】
帧头：固定为 0xAA 0x55
长度：帧总长（帧头到校验），包括校验字节
命令：
  0x01 - 上报温湿度
  0x02 - 心跳包
  0x03 - 设备注册
  0x81 - 控制LED（下行）
  0x82 - 控制蜂鸣器（下行）
设备ID：1~255
数据：根据命令不同格式不同
校验：从帧头到数据区所有字节的异或（XOR）

【0x01 上报温湿度 - 数据格式】
数据长度：6字节
┌──────────┬──────────┬──────────┐
│  温度高字节 │  温度低字节 │  湿度值    │
│  1字节    │  1字节    │  4字节     │
└──────────┴──────────┴──────────┘

温度 = (温度高字节 << 8 | 温度低字节) / 100.0  单位：°C
湿度 = 湿度值 / 100.0  单位：%

═══════════════════════════════════════════════════════════════
```

### 实际数据示例

```
场景：1号设备上报温度 25.5°C，湿度 60.0%

温度值 = 25.5 * 100 = 2550 = 0x09F6
  高字节 = 0x09
  低字节 = 0xF6

湿度值 = 60.0 * 100 = 6000 = 0x00001770
  4字节 = 0x00 0x00 0x17 0x70

数据区 = 09 F6 00 00 17 70（6字节）

完整帧：
帧头    长度  命令  设备ID  数据区                    校验
AA 55   0C    01    01     09 F6 00 00 17 70          ??

校验计算（XOR）：
AA ^ 55 = FF
FF ^ 0C = F3
F3 ^ 01 = F2
F2 ^ 01 = F3
F3 ^ 09 = FA
FA ^ F6 = 0C
0C ^ 00 = 0C
0C ^ 00 = 0C
0C ^ 17 = 1B
1B ^ 70 = 6B

最终帧：AA 55 0C 01 01 09 F6 00 00 17 70 6B
```

### 你在代码中如何解析

```typescript
// TypeScript 解析函数
function parseFrame(buffer: Uint8Array): { cmd: number; deviceId: number; data: unknown } | null {
  // 1. 检查帧头
  if (buffer[0] !== 0xAA || buffer[1] !== 0x55) {
    console.error("帧头错误")
    return null
  }

  // 2. 获取长度
  const length = buffer[2]
  if (buffer.length < length) {
    console.error("数据不完整")
    return null
  }

  // 3. 校验
  let checksum = 0
  for (let i = 0; i < length - 1; i++) {
    checksum ^= buffer[i]
  }
  if (checksum !== buffer[length - 1]) {
    console.error("校验失败，数据可能损坏")
    return null
  }

  // 4. 解析字段
  const cmd = buffer[3]
  const deviceId = buffer[4]
  const dataBytes = buffer.slice(5, length - 1)

  // 5. 根据命令解析数据
  switch (cmd) {
    case 0x01: // 温湿度
      const tempRaw = (dataBytes[0] << 8) | dataBytes[1]
      const temp = tempRaw / 100.0
      const humiRaw = (dataBytes[2] << 24) | (dataBytes[3] << 16) |
                      (dataBytes[4] << 8) | dataBytes[5]
      const humi = humiRaw / 100.0
      return {
        cmd,
        deviceId,
        data: { temperature: temp, humidity: humi }
      }

    case 0x02: // 心跳包
      return { cmd, deviceId, data: { type: "heartbeat" } }

    default:
      return { cmd, deviceId, data: dataBytes }
  }
}

// 使用
const rawData = new Uint8Array([0xAA, 0x55, 0x0C, 0x01, 0x01, 0x09, 0xF6, 0x00, 0x00, 0x17, 0x70, 0x6B])
const result = parseFrame(rawData)
console.log(result)
// { cmd: 1, deviceId: 1, data: { temperature: 25.5, humidity: 60 } }
```

## 四、粘包和分包问题

### 问题描述

```
UART是流式传输，没有天然的"帧边界"：

设备连续发送两帧：
  帧1: AA 55 0C 01 01 ...
  帧2: AA 55 0C 01 02 ...

实际接收到的可能是：
  ✅ 情况1：完整分开
  AA 55 0C 01 01 ... | AA 55 0C 01 02 ...

  ❌ 情况2：粘在一起
  AA 55 0C 01 01 ... AA 55 0C 01 02 ...

  ❌ 情况3：一帧被分成两次收到
  第一次：AA 55 0C 01 01 ...
  第二次：AA 55 0C 01 02 ...
```

### 解决方案：状态机解析

```typescript
// 状态机方式解析，解决粘包问题
class FrameParser {
  private buffer: number[] = []
  private state: "HEAD1" | "HEAD2" | "LENGTH" | "DATA" = "HEAD1"
  private expectedLength = 0

  onByteReceived(byte: number): object | null {
    this.buffer.push(byte)

    switch (this.state) {
      case "HEAD1":
        if (byte === 0xAA) {
          this.state = "HEAD2"
        } else {
          this.buffer = [] // 不是帧头，丢弃
        }
        break

      case "HEAD2":
        if (byte === 0x55) {
          this.state = "LENGTH"
        } else {
          this.buffer = [byte] // 可能是新的帧头
          this.state = byte === 0xAA ? "HEAD2" : "HEAD1"
        }
        break

      case "LENGTH":
        this.expectedLength = byte
        this.state = "DATA"
        break

      case "DATA":
        if (this.buffer.length >= this.expectedLength) {
          // 收到完整帧，解析
          const frame = new Uint8Array(this.buffer)
          this.buffer = []
          this.state = "HEAD1"
          return this.parseValidFrame(frame)
        }
        break
    }
    return null
  }

  private parseValidFrame(frame: Uint8Array): object | null {
    // ... 校验和解析
    return parseFrame(frame)
  }
}
```

## 五、JSON vs Protobuf vs 自定义二进制 对比

| 特性 | JSON | Protobuf | 自定义二进制 |
|------|------|----------|-------------|
| 可读性 | ✅ 很好 | ❌ 需要工具 | ❌ 很难读 |
| 数据大小 | ❌ 大（有字段名） | ✅ 小（二进制） | ✅ 最小 |
| 解析速度 | ❌ 慢（字符串解析） | ✅ 快 | ✅ 最快 |
| 内存占用 | ❌ 大 | ✅ 小 | ✅ 最小 |
| 开发效率 | ✅ 高 | ⚠️ 需要定义.proto | ⚠️ 需要写解析代码 |
| 版本兼容 | ✅ 容易 | ✅ 有字段编号 | ❌ 需要手动处理 |
| 工具支持 | ✅ 极好 | ✅ Google官方 | ❌ 自己写 |
| 适用设备 | 树莓派/Linux | ESP32+ | 所有MCU |

### 选择建议

```
设备能力强（树莓派/ESP32-S3）：
  └── 用 JSON（开发快）或 Protobuf（性能+兼容）

设备能力弱（STM32/ESP8266）：
  └── 用自定义二进制（省资源）

项目中两种都用：
  └── 设备→云端：二进制（省流量）
  └── 云端→App：JSON（方便处理）
```

## 六、Protobuf 快速入门

```protobuf
// sensor.proto
syntax = "proto3";

message SensorData {
  uint32 device_id = 1;
  float temperature = 2;
  float humidity = 3;
  uint64 timestamp = 4;
}

message ControlCommand {
  uint32 device_id = 1;
  enum CommandType {
    LED_ON = 0;
    LED_OFF = 1;
    BUZZER_ON = 2;
    RESET = 3;
  }
  CommandType cmd = 2;
  uint32 param = 3;  // 亮度、持续时间等
}
```

```typescript
// TypeScript 中使用（需要 protobufjs）
import protobuf from 'protobufjs'

// 加载 .proto 文件
const root = await protobuf.load("sensor.proto")
const SensorData = root.lookupType("SensorData")

// 编码（对象 → 二进制）
const message = SensorData.create({
  deviceId: 1,
  temperature: 25.5,
  humidity: 60.0,
  timestamp: Date.now()
})
const buffer = SensorData.encode(message).finish()
// buffer 是 Uint8Array，可以直接发MQTT

// 解码（二进制 → 对象）
const decoded = SensorData.decode(buffer)
console.log(decoded.temperature)  // 25.5
```

## 七、通信协议文档模板

这是你和嵌入式开发者必须一起写的文档：

```markdown
# XX项目设备通信协议 V1.0

## 1. 通信方式
- UART: 115200 8N1
- 或 MQTT: broker地址, Topic前缀

## 2. 帧格式
| 字段 | 长度 | 说明 |
|------|------|------|
| 帧头 | 2字节 | 0xAA 0x55 |
| 长度 | 1字节 | 总长度 |
| 命令 | 1字节 | 见命令表 |
| 设备ID | 1字节 | 1-255 |
| 数据 | N字节 | 根据命令 |
| 校验 | 1字节 | XOR |

## 3. 命令表
| 命令 | 名称 | 方向 | 数据格式 | 说明 |
|------|------|------|---------|------|
| 0x01 | 上报温湿度 | 设备→云端 | 温度(2B)+湿度(4B) | 每5秒上报一次 |
| 0x02 | 心跳包 | 设备→云端 | 无 | 每30秒一次 |
| 0x81 | 控制LED | 云端→设备 | 亮度(1B) | 0-255 |

## 4. 数据解析
### 4.1 温度
温度 = (高字节 << 8 | 低字节) / 100.0  (°C)

### 4.2 湿度
湿度 = 4字节整型 / 100.0  (%)

## 5. 错误处理
- 校验失败：丢弃该帧
- 命令未知：返回错误帧（0xFF）
- 数据长度不对：丢弃该帧

## 6. 版本历史
| 版本 | 日期 | 修改内容 |
|------|------|---------|
| V1.0 | 2024-01-01 | 初始版本 |
```
