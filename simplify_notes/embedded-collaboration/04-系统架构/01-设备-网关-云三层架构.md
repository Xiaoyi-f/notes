# 01 - 设备-网关-云三层架构——系统设计的"骨架"

---

## 一、为什么需要分层？

想象一下你要监控一个工厂，有100台设备：

```
❌ 错误的架构：每台设备直接连云端MQTT

  设备1 ──MQTT──►
  设备2 ──MQTT──►
  设备3 ──MQTT──►    云端Broker
     ...          ◄── 100台设备同时连接！
  设备100 ──MQTT──►

问题：
- 云端连接数爆炸（100台 × 每台保持长连接）
- 网络不稳定时，每台设备都要处理断线重连
- 设备直接暴露在外网，不安全
- 设备升级时要连100台，累死
```

```
✅ 正确的架构：设备 → 网关 → 云端

  设备1 ──UART/I2C──┐
  设备2 ──UART/I2C──┼──► 网关（树莓派/工控机）──MQTT──► 云端
  设备3 ──Modbus────┘    - 数据汇聚               - 统一出口
     ...                 - 协议转换               - 安全管理
  设备20 ──CAN──────┘    - 边缘计算               - 设备管理

问题解决了：
- 云端只看到1个网关连接
- 网关处理断线重连，设备不知道
- 设备在内网，不暴露
- 网关统一代理升级
```

## 三、每层的核心职责

### 感知层（设备端）

```
职责：
✅ 采集传感器数据（温度、压力、位置等）
✅ 执行控制命令（开关灯、调节电机）
✅ 简单的本地逻辑（按钮按下开灯，再次按下关灯）
✅ 异常时本地报警（蜂鸣器、LED闪烁）

不做：
❌ 复杂的业务逻辑（放在云端）
❌ 大数据存储（存不下）
❌ 网络协议处理（简单透传给网关）

通信方式：
- 近距离：UART、I2C、SPI（板级通信）
- 远距离：RS485+Modbus、CAN总线（几十米到几百米）
```

### 网络层（网关）

```
职责：
✅ 协议转换：把设备的UART/Modbus转成MQTT/HTTP
✅ 数据汇聚：收集多台设备数据，统一上报
✅ 边缘计算：本地预处理（过滤噪声、计算均值、判断阈值）
✅ 断网缓存：没网时存本地，有网时批量上报
✅ 设备代理：代管设备注册、OTA升级、心跳
✅ 安全防护：防火墙、数据加密、访问控制

典型硬件：
- 树莓派（低成本，适合原型）
- 工业网关（稳定，-40°C~70°C）
- 边缘计算盒子（带AI加速，做图像识别）
```

### 平台层（云端）

```
职责：
✅ 设备管理：注册、认证、分组、监控在线状态
✅ 数据存储：时序数据、配置数据、用户数据
✅ 业务逻辑：告警规则、自动化场景、数据分析
✅ 对外服务：REST API、WebSocket推送
✅ 运维管理：OTA升级、日志收集、远程诊断

技术栈：
- MQTT Broker：EMQX、Mosquitto
- 后端服务：Java Spring Boot / Node.js / Go
- 数据库：MySQL（用户/配置）、InfluxDB/TDengine（时序数据）
- 缓存：Redis（会话、实时状态）
```

## 五、架构选型决策树

```
你的系统有多少台设备？
│
├─ 1-5台（家庭/小型项目）
│   └─ 设备直接连WiFi → 云端MQTT
│      （不需要网关，简单直接）
│
├─ 5-50台（小型工厂/楼宇）
│   └─ 用一个网关汇聚 → 云端
│      （推荐树莓派/工控机做网关）
│
└─ 50+台（大型工厂/园区）
    └─ 多层网关架构
       区域网关1 ─┐
       区域网关2 ─┼──► 中心网关 ──► 云端
       区域网关3 ─┘
       （每个区域一个网关，再汇聚到中心）

设备分布范围？
├─ 同一个房间/设备内
│   └─ UART / I2C / SPI
├─ 同一层楼/厂房
│   └─ RS485 + Modbus / CAN
├─ 同一园区/楼宇
│   └─ 以太网 / WiFi / LoRa
└─ 分散在城市各地
    └─ 4G / NB-IoT
```
